## 2. 個人運用の開始前

1. `debug`の個人用アプリをインストールする。アプリ情報で「Mockup」「0.1.0」「個人用」を確認する。
2. [詳細設計書の受入確認](20_詳細設計書.md#9-実装時の受入確認)のT-01〜T-30、T-33、T-34の個人用部分とT-35を確認する。T-22の購入情報保持は購入用DBを導入する将来版で確認する。
3. 架空の金額を使い、初期10,000円→商品1,500円・受取2,000円→実残高11,400円→次回10,000円の例を通す。予定11,500円、過不足-100円、取出1,400円になることを確認する。
4. 機内モードで業務操作と端末内へのCSV / JSON出力ができ、再起動・通常更新後も記録が残ることを確認する。
5. 課金ボタン・課金SDK・自動通信がなく、問い合わせだけが明示操作で外部ブラウザーを開くことを確認する。
6. 架空の試験データを全クリアし、実運用を始める。実データを使い始めてから試験用に全クリアしない。

試験結果はこの表を実施後に更新する。新たなテスト仕様書は作らず、期待結果は詳細設計書で一元管理する。

## 3. 日々の運用と更新

- 稼働前に実際の持出額で開始し、現金受渡し後に記録する。補充・取出しもその時点で登録する。
- 稼働終了時に現金を数えて締める。差額があれば履歴を確認し、理由なく合う数値へ書き換えない。
- 締め後はCSVまたはJSONを端末の保管用フォルダーへ出力し、更新前には念のため再出力する。出力ファイルを開けることと、最後のレジが含まれることを確認する。
- 初期版には再取込・復元がない。出力は記帳・確認用の控えであり、アプリDBを復元するバックアップではない。
- 日々の記録、画面写真、実金額を公開GitHubに置かない。不具合報告は架空の値に置き換える。
- 個人用の更新は同じアプリID・同じデバッグ鍵のAPKを上書きインストールする。鍵の変更や紛失時は一旦止め、元アプリを残して出力を確保する。

自動クラウドバックアップ・端末移行を使わないため、端末の故障・紛失、データ消去、アンインストールで内部履歴を失う。全クリアも取り消せない。書き出したファイルは自動で消去されず、利用者が保存先で管理する。

個人運用の目安は**2週間以上かつ10回以上のレジ締め**とする。これは自分で使い勝手を確かめる目安であり、Google Playのテスト要件ではない。計算間違い、記録消失、二重保存、出力不整合があれば修正して該当試験を再確認し、問題が残ったまま公開しない。

不具合時は旧版のアンインストールやDB初期化を避け、操作手順・アプリ版を控えて修正版を上書きする。DBの版を戻す単純なダウングレードは行わない。将来の公開後も、公開停止・配信停止と、利用端末のデータ削除は別の操作として扱う。

## 4. 個人用から公開版へ移るとき

個人用IDは`io.github.mock108.ubaregi.debug`、公開版IDは`io.github.mock108.ubaregi`とする。両方を同じ端末に置けるが、DBは共有しない。[アプリIDの公式説明](https://developer.android.com/build/configure-app-module)

個人用で最後のレジを締めて記録を出力し、公開版では実際の持出額を入力して新しいレジを始める。過去履歴は個人用アプリと出力ファイルに残す。公開版へ自動で移らず、JSONからの復元もできない。記録の確認が終わる前に個人用をアンインストールしない。

自動移行が必要になった場合は、別途復元仕様・試験を追加してから対応する。今は個人用と公開版の分離を保ち、公開署名を前倒しして用意する必要はない。

## 5. 後日設定する場所

公開準備時に、[release.properties.example](../release.properties.example)をリポジトリ直下の`release.properties`へコピーする。現時点でコピーは不要。この見本はまだビルドから読まれず、公開用ビルド処理を作る際に読み込みを実装する。

| キー・設定場所 | 決定値または後日行うこと |
| --- | --- |
| developerName | `Mockup`。Play上の本人確認情報は登録時に本人が正しく入力する |
| billingEnabled | 当初`false`。購入実装・試験・ポリシー更新完了後にのみ`true` |
| billingProductId | `developer_support`。Playに同じIDで商品登録する |
| supportEmail | 公開される窓口用メールを用意して記入。個人の既存メールを自動採用しない |
| privacyPolicyUrl | 下記のポリシーを公開し、ログイン不要で閲覧できる実URLを記入 |
| storeFile | 後日作るアップロード鍵の絶対パス。鍵はリポジトリ外に保管 |
| storePassword / keyAlias / keyPassword | 後日作る鍵の実際の値。テンプレートや文書へ転記しない |
| applicationId / namespace | 公開版`io.github.mock108.ubaregi`。`app/build.gradle.kts`に定義 |
| versionName / versionCode | 初期値`0.1.0` / `1`。公開時の実際の版に更新し、配布ごとにcodeを増加 |

実ファイルはGit管理対象外とする。公開用の署名設定が不足する場合、releaseビルドを明確な説明で停止し、デバッグ鍵へ自動で切り替えない。debugビルドでは公開設定を要求しない。`billingEnabled=true`だけで購入が動くわけではなく、SDK導入・購入処理・商品登録が別途必要になる。

## 6. Google Play公開を決めた後の作業

1. 開発者アカウントを登録して本人確認を行う。開発者表示名はMockupとする。法的名称や住所等が求められる場合は実際の情報を本人が登録する。
2. 公開アプリを作成し、無料、日本、日本語、広告なし、カテゴリ「ツール」を初期値とする。アプリの実態と公開時点の選択肢に合わせる。
3. 公開用メールを用意し、[プライバシーポリシー](50_プライバシーポリシー.md)を実装に照合して更新する。GitHub Pagesで読み取り専用の公開ページを用意する方針とし、実際のページができてからURLを設定する。編集画面やPDFは指定しない。
4. アップロード鍵を作成してリポジトリ外で保管・バックアップし、Play App Signingを設定する。公開用AABを署名する。debug署名のAPKを公開申請しない。
5. 企画書のR-12に従い、公開版には開発支援購入を用意し、詳細設計の将来仕様を実装する。「任意」は利用者が購入するかを選べる意味であり、公開版での機能提供は必須とする。`developer_support`を消費型の1回購入として登録し、日本の設定希望価格を100円とする。実際に表示する商品名・価格はPlayの商品情報から取得する。全業務機能無料を維持する。
6. 購入を有効にする前に、Google Play Billingの現行規約・対応ライブラリ・確認方法を見直す。バックエンドなしの構成が要件を満たすか確認し、未充足なら購入を無効のまま個人運用を続け、公開を保留する。プライバシー文面にはGoogle側の購入処理と端末内の処理用情報を追記する。
7. データセーフティ、広告、対象年齢、コンテンツレーティング、アプリへのアクセス等を実装に即して申告する。ログイン不要。外部SDKも確認し、「収集なし」を思い込みで選ばない。
8. 実際のアイコン、4画面のスクリーンショット、必要な紹介画像を作る。Uberのロゴや公式と誤認する素材は使用しない。
9. 個人用で確認済みの業務試験を公開版でも確認し、購入の成功・取消・保留・再確認・再購入、ストア文面とManifest・同梱文面の一致を検証する。
10. 登録したアカウントに必要なテストを完了し、本人が公開を決めてから申請する。公開後はIssuesとPlay Consoleの案内を確認する。

アプリがデータを収集しない場合も、Google Playのプライバシーポリシーとデータセーフティの要件を確認する。2023-11-13以降に作成された対象の個人アカウントでは、製品版へのアクセス前に12人以上・連続14日間のクローズドテスト等が案内されている。今回の本人だけの個人運用で代替した扱いにはしない。条件は将来の登録・公開時点で再確認する。[ユーザーデータのポリシー](https://support.google.com/googleplay/android-developer/answer/10144311?hl=ja) / [データセーフティ](https://support.google.com/googleplay/android-developer/answer/10787469?hl=ja) / [個人アカウントのテスト要件](https://support.google.com/googleplay/android-developer/answer/14151465?hl=ja)

公開連絡先・ストア設定は[アプリ作成と設定](https://support.google.com/googleplay/android-developer/answer/9859152?hl=ja)、署名は[Android公式手順](https://developer.android.com/studio/publish/app-signing)、ポリシーの公開方法は[GitHub Pages](https://docs.github.com/ja/pages/getting-started-with-github-pages/what-is-github-pages)を参照する。購入については[Google Play Billing](https://developer.android.com/google/play/billing/integrate?hl=ja)と[支払いポリシー](https://support.google.com/googleplay/android-developer/answer/9858738?hl=ja)を確認する。

## 7. ストア掲載文面の下書き

短い説明：

> 現金払いの配達に。初期釣銭、おつり計算、現金の記録、レジ締めをシンプルに。

詳しい説明：

> ウバレジは、Uber Eatsの現金払いの配達で扱うお金を記録する非公式の補助アプリです。初期釣銭の登録、おつりの計算、受渡し履歴の編集、釣銭の補充・取出し、レジ締めができます。
>
> 計算と記録はオフラインで利用でき、ログインや広告はありません。帳簿作成の元データとして独自CSV・JSONを書き出せます。会計ソフトへの直接記帳、Uberとの連携、配達報酬や税金の計算は行いません。
>
> 履歴は端末内に保存します。自動バックアップ・端末移行・ファイルからの復元には対応しません。アンインストールやデータ消去で履歴が失われるため、必要な記録はあらかじめ出力してください。問い合わせでは外部ブラウザーでGitHubを開きます。
>
> 開発者：Mockup。本アプリはUberまたはUber Eatsの公式アプリではありません。Android 17向けに開発しています。

公開版で購入機能の実装・有効化を確認後、次の文を詳しい説明に追加する：

> すべての機能を無料で利用できます。任意の開発支援購入を用意していますが、購入による機能追加や利用制限の解除はありません。購入・購入確認を操作したときはGoogle Playに接続します。

この文面は設計に基づく下書きであり、未実装の機能を現時点でストアに掲載しない。公開直前に実際の動作・購入の有無・対応OSへ合わせる。
