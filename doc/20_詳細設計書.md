# ウバレジ 詳細設計書

| 項目 | 内容 |
| --- | --- |
| 文書番号・版 | 20 / 0.5 |
| 対象 | 4画面、計算・保存・履歴編集・出力・任意購入 |

金額や操作の細部は本書の初期仕様を採用する。画面はMaterial 3標準部品を中心に、青を基調とした単色の配色・システム設定に従う明暗切替・標準フォントで構成する。独自の装飾やアニメーションは増やさない。アプリアイコンは自作の簡単な釣銭・電卓モチーフとし、Uberのロゴや公式アイコンを使わない。実際の素材は画面実装時に作成する。

個人運用版を先に実装する。第5.4節の購入処理と第6.5節の購入情報保存は公開版の仕様とし、公開準備時に実装する。アプリID・初期版・開発者名は[30_開発環境構築手順](30_開発環境構築手順.md)に従う。

## 1. 共通仕様

### 1.1 金額入力・表示

| 項目 | 仕様 |
| --- | --- |
| 単位 | 日本円、1円単位 |
| 入力形式 | 数字キーボード。半角数字と全角数字を受け付け、全角数字は半角へ正規化 |
| 貼り付け | 前後空白のみ除去。通貨記号・区切りカンマ・小数点・符号・数式はエラー |
| 未入力 | 0として扱わず、未入力として保持 |
| 上限 | 入力1項目あたり9,999,999円 |
| 0円可 | 初期釣銭、受取金額の入力途中、実残高、次回釣銭 |
| 1円以上 | 商品金額、補充額、途中取出額 |
| 負数 | 入力は不可。過不足など算出結果では表示可 |
| 表示 | 例：`1,500円`、`不足 100円`、`超過 100円`、`過不足なし` |
| 保存形式 | `Long`の整数。画面の桁区切りは保存しない |

金額・集計の加減算はオーバーフローを確認する。上限超過や不正値では保存せず、入力欄の近くに理由を表示する。

### 1.2 時刻・並び・画面復帰

- 日時は端末時計からUTCのInstantとして保存し、画面ではAsia/Tokyoで表示する。
- 取引の日時は受渡しを記録した時点。初期版では日時の手動編集・過去への明細追加を設けない。
- レジは開始連番、明細はレジ内連番で順序を決める。同じ日時や時計の逆行でも順序を維持する。
- 通常の新規起動先はホーム。OSによる画面再生成時は遷移先と入力を可能な範囲で復元する。
- 保存前の入力はSavedStateHandle等で保持するが、強制停止・再起動後の永続復元は保証しない。「未保存」として表示する。
- 戻る操作は、編集ダイアログ → 元画面 → ホームの順。変更がある編集を破棄するときは確認する。
- 保存中は対象操作を無効化する。成功通知はDBトランザクションの確定後に表示する。

## 2. S-01 ホーム画面

### 2.1 配置案

```text
ウバレジ
レジ：未開始 / 稼働中
［稼働中なら：開始日時・現金回収額・予定残高］

[ おつり計算 ]
[ レジ締め / 初期釣銭 ]
[ アプリ情報 ]

データを書き出す（全履歴）
[ JSONで保存 ]  [ CSVで保存 ]
```

### 2.2 表示・操作

| ID | 項目 | 処理 |
| --- | --- | --- |
| H-01 | レジ状態 | OPENがあれば開始日時・現金回収額・予定残高。なければ「レジ未開始」 |
| H-02 | おつり計算 | S-03へ。OPENがあればそのレジを初期選択 |
| H-03 | レジ締め / 初期釣銭 | S-02へ。稼働中なら締め操作、未開始なら開始入力を表示 |
| H-04 | アプリ情報 | S-04へ。表示だけでは通信しない |
| H-05 | JSON / CSVで保存 | 形式に応じたファイル保存処理。詳細は第8節 |

予定残高は現金を実際に数えた額とは区別して表示する。OPENがない場合、前回の締め結果を現在の残高として表示しない。

### 2.3 出力操作

1. 全履歴の出力であることと、ローカル保存先の選択を案内する。
2. Androidの保存先選択を開く。利用者が取り消した場合は何も変更しない。
3. 保存先確定後にDBの一貫したスナップショットを取得して出力する。
4. 書込みとストリーム終了が成功してから「保存しました」と表示する。
5. 容量不足・権限喪失・提供元エラーなら成功扱いにせず、元データは維持する。

履歴0件でも、JSONは空配列とメタ情報、CSVはヘッダーとメタ情報行を出力できる。出力ボタンの連打は処理中無効とする。

## 3. S-02 レジ締め / 初期釣銭金額入力画面

### 3.1 配置案

```text
＜ ホーム       レジ締め / 初期釣銭

未開始時：
  初期釣銭 [          ] 円
  ［前回の次回釣銭を候補表示］
  [ この金額でレジ開始 ]

稼働中：
  初期釣銭・現金回収額・予定残高
  [ 釣銭を補充 ]  [ 現金を取り出す ]
  補充・取出し履歴 → 編集 / 取消
  実残高   [          ] 円
  次回釣銭 [          ] 円
  過不足・締め時の取出額
  [ レジを締める ]

レジ履歴（新しい順）
  開始日時 / 状態 / 現金回収額 / 過不足
  → 詳細・編集 / このレジの取引を見る
[ 全レジ履歴をクリア ]
```

### 3.2 初期釣銭・開始

| ID | 操作 | 詳細 |
| --- | --- | --- |
| Rg-01 | 候補表示 | 最新の締め済みレジの次回釣銭を入力欄に入れ、由来を表示。初回は空欄 |
| Rg-02 | 開始 | 入力検証後、UUID・開始連番・開始日時を付け、OPENとして保存 |
| Rg-03 | 初期釣銭修正 | 稼働中の初期釣銭を修正できる。修正前後の予定残高を確認して保存 |

開始は明示ボタンで行い、候補を表示しただけで登録しない。既にOPENがあれば二重開始を拒否して現在のレジを表示する。開始後の現金補充はRg-03ではなく補充明細として記録する。

### 3.3 釣銭補充・現金取出し

稼働中のレジに対し、画面内ダイアログで金額を入力する。種別は`CASH_IN`（補充）または`CASH_OUT`（取出し）。理由の自由記述や会計科目は初期版では設けない。

- 補充は現金を手元に追加した後、取出しは実際に取り出した後に記録する。
- 保存後は予定残高を更新する。既存明細は同じダイアログで金額を編集できる。
- 種別を間違えた場合は取消後、稼働中の正しい種別で新規登録する。
- 取消は金額の逆符号の明細を追加せず、元明細を取消済みにする。
- 予定残高が負になる場合は記録漏れの可能性を表示し、確認後の保存を認める。自動で0に補正しない。

締め済みレジの補充・取出し履歴も詳細ダイアログから編集・取消できるが、新しい明細は追加できない。

### 3.4 レジ締め

1. 最新の明細から予定残高Eを計算する。
2. 利用者が締め時の取出し前の手元現金Rを数えて入力する。Eを実残高として自動確定しない。
3. 次回釣銭Nを入力する。初期候補は当該レジの初期釣銭Fだが、利用者が確認する。
4. `0 <= N <= R`を検証し、現金回収額K、予定残高E、実残高R、過不足D、増減G、取出額Wを表示する。
5. 「レジを締める」で確認ダイアログを開く。D≠0なら「不足 / 超過○円のまま締めます」と明示する。
6. 確認時に同じレジの版番号を再確認し、変化がなければR・N・締め日時・CLOSEDを一括保存する。
7. 完了後は締め結果を表示する。次回のレジは自動開始しない。

明細0件のレジも締められる。確認中に明細が変更されたら集計を読み直し、再確認を求める。締めボタンの再実行で締め日時を上書きしない。

### 3.5 レジ履歴・編集

- レジ履歴には稼働中と締め済みを含め、開始連番の降順で表示する。
- 選択すると、初期釣銭、全集計、実残高、次回釣銭、作成・修正日時を表示する。
- 編集できる項目はF、締め済みならRとN。算出値、ID、連番、開始・締め日時は直接編集しない。
- 「このレジの取引を見る」でS-03に対象レジIDを渡す。S-03から戻ると元の履歴選択を維持する。
- 明細編集後は元レジの集計を更新し、CLOSEDなら「締め後に修正済み」を表示する。
- 修正前後の予定残高・過不足を保存前に表示する。他レジの初期釣銭を自動で修正しない。
- 締め済みレジの再オープン、開始日時の変更、単独レジの物理削除は初期版では行わない。

### 3.6 レジ履歴クリア

「全レジ履歴をクリア」は、すべてのレジ・現金受渡し明細・補充取出し明細を削除する。対象には稼働中のレジも含める。

確認ダイアログでレジ件数・明細件数・稼働中レジの有無と、復元できないことを表示する。「キャンセル」「ホームで先に出力」「すべて消去」の選択肢を用意する。消去対象の一覧表示中にデータが変わった場合は件数を再確認する。

消去は一括トランザクションで実施し、全画面の選択・入力下書きを破棄してホームを未開始状態にする。次回釣銭候補も消える。DatasetMetaのID・連番カウンターは維持し、全体版番号を1増やす。購入の未処理情報とGoogle Play上の購入は対象外。既に書き出した外部ファイルは消去できない。

## 4. S-03 おつり計算電卓画面

### 4.1 配置案

```text
＜ ホーム / レジ履歴      おつり計算
対象レジ：稼働中 / 締め済み日時 / 未開始

商品金額           [          ] 円
お客様支払金額     [          ] 円
おつり                 500 円

[ 入力クリア ]   [ 受渡しを記録 ]
［未開始なら：計算のみ利用可 / レジを開始する］

対象レジの受渡し履歴（新しい順）
時刻 / 商品金額 / 受取金額 / おつり / 取消状態
→ 金額を編集 / 取消
```

### 4.2 入力・計算・保存

| ID | 操作・状態 | 仕様 |
| --- | --- | --- |
| C-01 | 商品金額入力 | 実際の現金請求額を入力。Uberから取得しない |
| C-02 | お客様支払金額入力 | 実際に受け取った現金総額。差額をチップと推測しない |
| C-03 | 計算 | 有効な2入力が揃ったら`P - A`を即時計算 |
| C-04 | 受取不足 | `P < A`なら「あと○円不足」。おつりに負額を表示せず、保存を無効化 |
| C-05 | 同額受取 | `P = A`なら「おつり0円」。保存可能 |
| C-06 | 受渡しを記録 | OPENの対象レジへPAYMENT明細を保存。成功後に入力を空にして商品金額へフォーカス |
| C-07 | 入力クリア | 入力だけを消去する。保存済み履歴は変更しない |
| C-08 | レジ未開始 | 計算可・保存不可。「レジを開始する」でS-02へ移動し、入力を可能な範囲で保持 |
| C-09 | 締め済みレジ選択中 | 新規入力・保存を無効化し、対象履歴の編集だけを提供 |

表示したおつりは実際に返す予定額であり、紙幣・硬貨の在庫による払出し可否は判定しない。金額計算だけでは履歴を作らない。お客様支払金額には釣銭不要のチップを混ぜない。

### 4.3 受渡し履歴・編集

履歴は選択したレジのPAYMENT明細だけを、明細連番の降順で表示する。別レジはS-02の履歴から選ぶ。取消済みはラベル付きで表示し、合計から除外する。

編集ダイアログでは商品金額A・受取金額Pを編集できる。おつり・現金増減は自動計算で、直接編集しない。新規登録と同じ検証を適用し、同一IDを更新する。保存後は履歴、ホームの要約、レジの集計を更新する。

取消は確認後に`is_voided = true`とする。試作では取消の解除・取消済み明細の編集は行わない。稼働中なら必要に応じて正しい取引を新規登録する。締め済みの誤記修正は取消より金額編集を優先する。

### 5.2 個人運用版に同梱する説明文

> ウバレジは、Uber Eatsの配達で扱う現金とおつりを記録する非公式の補助アプリです。
>
> 計算・履歴・レジ締めはオフラインで利用でき、記録は端末内に保存します。広告配信、利用状況の解析、記録の自動送信は行いません。お問い合わせでは外部ブラウザーでGitHubを開きます。業務の記録を自動送信することはありません。
>
> CSV / JSONは、操作したときだけ選んだ保存先へ書き出します。クラウド保存先や外部の変換サイトを利用すると、そのサービスによる通信・保存が発生する場合があります。
>
> 自動バックアップは行いません。アプリの削除やデータ消去、端末故障で記録が失われます。出力したファイルをアプリへ戻す機能はありません。必要な記録は手動で書き出してください。
>
> 表示される現金回収額は配達報酬や利益ではありません。すべての機能は無料です。この個人運用版では開発支援の購入は利用できません。

アプリの正式な取扱い文面は[50_プライバシーポリシー](50_プライバシーポリシー.md)を同梱する。将来課金を有効にするときは、本概要文とポリシーを実装に合わせて更新する。

### 5.3 問い合わせ

[GitHub Issues](https://github.com/mock108/ubaregi/issues)を問い合わせ先とする。アプリでは`https://github.com/mock108/ubaregi/issues`を固定URLに設定する。

押下時には外部サイトであること、投稿にはGitHub側のログインが必要な場合があること、公開Issueに顧客情報や配達記録を載せないことを短く案内する。アプリ内ログインは設けない。URLへ明細や端末情報を付加せず、Issueを自動投稿しない。ブラウザーがない場合はエラーを表示し、固定URLのコピーを提供する。

### 5.4 任意の開発支援購入

**本節は将来の公開版の仕様。** 個人用では購入SDKを組み込まず、`BILLING_ENABLED = false`として購入・購入確認ボタンを隠す。「開発支援の購入は公開版で提供予定です」という説明だけ表示する。将来は画面呼出し部分を小さな購入処理クラスへ接続し、業務処理から分離する。

- 商品は1種類の消費型1回購入。商品IDは`developer_support`、名称は「開発支援（任意）」、日本の設定希望価格は100円。実際の商品登録と動作確認は公開準備時に行う。
- アプリ情報を開くだけではBilling接続しない。「開発を応援する」の押下後に接続・商品取得する。
- Google Playから得た商品名・価格と「任意 / 全機能無料 / 機能追加なし」を確認ダイアログに表示し、次の購入操作でGoogle Playの購入画面を起動する。
- 価格取得失敗・商品未設定・Play未対応の環境では購入を開始できない。無料機能はそのまま利用できる。
- 購入ボタン連打を無効にし、最新の商品情報を使う。価格をコード内の固定円額で置き換えない。
- 成立状態が`PURCHASED`の場合のみ、対象商品・パッケージ・署名等を確認し、未処理トークンを記録して`consumeAsync`を実行する。
- `PENDING`は「お支払い待ち」と表示し、消費・成功表示をしない。ユーザーキャンセルは購入失敗と区別する。
- 同じトークンは同じ処理として扱い、二重処理しない。消費成功後は未処理情報を削除する。
- 消費応答を受け取れなかった場合は次回の手動確認でPlayの所有状態と突き合わせる。状態を確定できない場合に購入成功を捏造しない。
- 通信は購入・手動確認の操作とその継続中に限る。画面退出時に未処理状態を残し、アプリ起動時や定期的な自動照会は行わない。
- 再購入前にも未消費購入を照会・処理する。処理待ちなら新たな購入を進めない。
- 購入確認期限内に再処理できないとGoogle Playで自動返金される場合がある。確認期限とクライアントのみの制約は基本設計書第8節に従う。
- 支援者専用の権限は作らず、過去の支援履歴の復元画面も設けない。購入履歴はGoogle Play側で確認できる旨を案内する。

レジ履歴クリアによって未処理購入トークンを失わせない。購入トークン・署名・課金情報はCSV / JSON・公開ログ・GitHubへ出力しない。

## 6. 永続データの詳細

### 6.1 共通ルール

DBスキーマ版は初期値1とし、出力フォーマットの`schema_version`とは別に管理する。UUIDは作成時に生成し、修正で変更しない。各レコードの`revision`は1から始め、変更ごとに1増やす。

日時はDBではUTCのepoch milliseconds、出力ではUTCのISO 8601文字列（例：`2026-09-07T03:00:00.000Z`）とする。UIだけ日本時間に変換する。端末時刻の正確さを保証しないため、編集競合・出力の新旧判定には日時ではなく版番号を使う。

### 6.2 DatasetMeta（1行）

| 項目 | 型 | 仕様 |
| --- | --- | --- |
| singleton_id | INTEGER | 固定値1、主キー |
| dataset_id | TEXT | 初回初期化時のUUID。端末内データ集合の識別用で、端末識別子ではない |
| snapshot_revision | INTEGER | 初期値0。業務データを変更したトランザクションごとに1増加 |
| next_session_sequence | INTEGER | 次のレジ連番。開始ごとに1増加、クリア後も再利用しない |

全クリアでもdataset_idを維持する。アプリデータの完全消去・再インストールでは新しくなる。出力だけでは版番号を増やさない。

### 6.3 RegisterSession

| 項目 | 型 | 必須・制約 |
| --- | --- | --- |
| id | TEXT | UUID、主キー |
| sequence | INTEGER | 全レジで一意の開始連番 |
| status | TEXT | `OPEN` / `CLOSED` |
| open_slot | INTEGER? | OPENは1、CLOSEDはNULL。一意インデックスと状態制約でOPENを最大1件にする。出力対象外 |
| opened_at | INTEGER | 初回開始日時、変更不可 |
| closed_at | INTEGER? | OPENはNULL、CLOSEDは必須。初回締め後は変更不可 |
| opening_float_yen | INTEGER | 初期釣銭F。0〜9,999,999 |
| actual_cash_yen | INTEGER? | 実残高R。OPENはNULL、CLOSEDは0〜9,999,999 |
| next_float_yen | INTEGER? | 次回釣銭N。OPENはNULL、CLOSEDは0〜R |
| created_at | INTEGER | 作成日時、変更不可 |
| updated_at | INTEGER | レジ本体または子明細の最新変更日時 |
| revision | INTEGER | 子明細の追加・編集・取消、締め、本体編集でも増加 |
| close_revision | INTEGER? | 初回締め直後のrevision。OPENはNULL、以後固定。出力対象外 |

`CLOSED && revision > close_revision`なら画面に「締め後に修正済み」を表示する。次回釣銭候補は`CLOSED`のうち最大sequenceの値を読む。別の設定値として二重保存しない。

### 6.4 CashEntry

| 項目 | 型 | 必須・制約 |
| --- | --- | --- |
| id | TEXT | UUID、主キー。新規保存リクエストの重複防止にも使用 |
| session_id | TEXT | RegisterSessionへの外部キー。別レジへの移動不可 |
| sequence | INTEGER | レジ内の連番。`(session_id, sequence)`で一意 |
| kind | TEXT | `PAYMENT` / `CASH_IN` / `CASH_OUT`。登録後の種別変更不可 |
| occurred_at | INTEGER | 現金受渡し・補充・取出しを記録した日時。変更不可 |
| product_amount_yen | INTEGER? | PAYMENTのみ必須。1〜9,999,999 |
| received_amount_yen | INTEGER? | PAYMENTのみ必須。商品金額以上、9,999,999以下 |
| amount_yen | INTEGER? | CASH_IN / CASH_OUTのみ必須。1〜9,999,999 |
| is_voided | INTEGER / Boolean | 初期値false。取消でtrue |
| created_at | INTEGER | 初回作成日時 |
| updated_at | INTEGER | 最終修正・取消日時 |
| revision | INTEGER | 初期値1、編集・取消で増加 |

種別に使わない金額列は必ずNULLとする。顧客名・住所・注文ID・位置情報・自由メモは保存しない。おつりや現金増減は入力値から計算するため、DBの独立した変更可能な列にしない。

### 6.5 PurchaseProcessing

個人運用版には作成しない。課金機能を追加する際に、業務DBから分離した保存処理として以下を実装する。

購入トークンを主キーとして、対象商品ID、`PENDING` / `PURCHASED` / `CONSUME_RETRY`等の処理状態、照合に必要な購入応答、最終試行日時を最小限保持する。業務テーブルとの外部キーを持たず、業務のsnapshot_revisionを更新しない。消費が確定した情報は削除し、課金情報の長期保存・全件の購入履歴DBを作らない。

## 7. 保存・再計算の処理契約

### 7.1 明細の算出値

| kind | change_yen | cash_in_yen | cash_out_yen | net_cash_yen |
| --- | --- | --- | --- | --- |
| PAYMENT | `received - product` | `received` | `change` | `product` |
| CASH_IN | NULL | `amount` | 0 | `amount` |
| CASH_OUT | NULL | 0 | `amount` | `-amount` |

取消済み明細も元の金額・算出値を履歴と出力に残す。ただしレジ集計には含めない。金額を0へ書き換えて取消を表現しない。

### 7.2 レジ集計

対象レジの`is_voided = false`の明細について計算する。明細がなければ合計は0。

```text
payment_collected_yen = PAYMENTのproduct_amount_yen合計
cash_in_yen           = 明細のcash_in_yen合計
cash_out_yen          = 明細のcash_out_yen合計
net_cash_yen          = cash_in_yen - cash_out_yen
expected_cash_yen     = opening_float_yen + net_cash_yen

CLOSEDのみ：
difference_yen        = actual_cash_yen - expected_cash_yen
actual_change_yen     = actual_cash_yen - opening_float_yen
withdrawal_yen        = actual_cash_yen - next_float_yen
```

`cash_in_yen`に初期釣銭Fを、`cash_out_yen`に締め時の取出額Wを足さない。途中の補充・取出しは含む。OPENの締め関連算出値はNULLとし、0円と区別する。

### 7.3 操作単位

| 操作 | 同一トランザクションに含める処理 |
| --- | --- |
| レジ開始 | OPEN不在確認、レジ追加、開始連番更新、全体版番号更新 |
| 新規明細保存 | IDによる保存済み確認を最初に実施。同じ内容なら変更せず成功済み、異なる内容なら競合。同じIDがない場合だけ対象レジがOPENか確認し、明細追加、親レジ版番号更新、全体版番号更新 |
| 明細編集・取消 | 明細と親レジの版番号確認、検証、明細更新、親レジ版番号更新、全体版番号更新 |
| レジ締め | OPENと版番号確認、明細再集計、R・N検証、CLOSED化、close_revision設定、全体版番号更新 |
| レジ本体修正 | 版番号確認、F・R・N検証、更新、全体版番号更新 |
| 全履歴消去 | 確認時の全体版番号照合、子明細全削除、レジ全削除、全体版番号更新 |

UI側だけで排他せず、DB側にもOPENの一意性、外部キー、種別・金額・状態の制約を置く。金額演算エラー・保存失敗時は全体をロールバックする。

保存用UUIDは入力下書きにつき1つ発行して再試行時にも使う。新規明細保存の再試行では、同一トランザクション内でレジ状態の判定より先に保存済みIDを確認する。同じID・同じ内容が保存済みなら、レジが締め済みでも成功済みとして扱う。別内容ならレジ状態にかかわらず競合とし、上書きや新しいIDでの自動再登録を行わない。同じIDがない場合に限り、対象レジがOPENであることを確認して新規保存する。

同じ内容かの比較対象は、親レジID、種別、種別に応じた入力金額とする。日時・連番・revision等のDB管理値は比較対象外とし、成功済みの再試行では既存明細・親レジ・全体版番号・締め日時を一切変更しない。取消済みの場合も取消状態を維持して現在の明細を表示する。成功後にUUIDを破棄し、次の入力用に新規発行する。画面再生成時にも同じ照合を行い、IDがあるだけで内容の異なる下書きを成功済み扱いしない。

更新は読み込んだrevisionを条件に行い、一致しなければ最新データを読み直して再編集する。出力用の一時ファイルを除き、DBと設定ファイルをまたぐ業務上の一括更新は作らない。

### 7.4 障害時の扱い

| 状況 | 表示・回復 |
| --- | --- |
| 必須未入力・範囲外 | 欄の近くで理由を説明。入力は維持 |
| 受取不足 | 不足額を表示して記録不可 |
| 保存時にレジが締め済み | 保存済みIDの照合を優先。同じID・同じ内容なら変更せず成功済み、異なる内容なら競合。同じIDがなければ新規保存を拒否して対象レジを更新表示。下書きを別レジへ自動移動しない |
| 同時編集・古い画面 | 最新データを読み直し、再確認 |
| ストレージ不足 | 保存失敗として入力を維持。保存済み表示を出さない |
| DB読込み・移行失敗 | 書込みを止め、データを自動消去しない。再起動案内と利用可能なアプリ情報を表示 |
| 外部保存の取消 | 状態変更なし |
| 外部保存の途中失敗 | 不完全なファイルの可能性を伝え、新規保存での再試行を案内 |
| Play・ブラウザー利用不可 | 当該機能の利用不可を表示。業務操作は継続可能 |

## 8. 出力フォーマットv1

### 8.1 共通契約

| 項目 | 仕様 |
| --- | --- |
| 対象 | 出力時に存在する全レジ・全明細。期間絞込みは初期版で設けない |
| 性質 | 全量スナップショット。新規分だけの差分ファイルではない |
| 出力版 | schema_version = 1 |
| 金額 | 通貨JPY、円単位のJSON整数 / CSV整数文字列。算出値では負数可 |
| 日時 | UTC、ミリ秒付きISO 8601。画面表示の日本時間と区別 |
| 未確定値・対象外値 | JSONはnull、CSVは空欄。0円とは区別 |
| メタ情報 | dataset_id、snapshot_revision、exported_at、app_version |
| 業務データ以外 | 購入情報、内部制約用列、端末情報、保存先URIは含めない |
| 並び | レジはsequence昇順、明細は親レジsequence→明細sequence昇順 |
| 出力ファイル名 | ubaregi_YYYYMMDD_HHmmss_SSS_r{snapshot_revision}.json または .csv（日時部分は日本時間） |

ファイル名の重複は保存先の確認に従う。未知のファイルをアプリが勝手に上書き・消去しない。書込みにはOSの文書作成UIを使い、JSONのMIMEはapplication/json、CSVはtext/csvとする。

保存先が決まった時点で一貫した読取りトランザクションからメタ情報・全レジ・全明細を読み、内部キャッシュの一時ファイルへ直列化する。外部の遅い保存先へ書く間はDBトランザクションを保持しない。出力ボタン押下後でも、この読取り開始前の変更は含まれる。

内部一時ファイルは成功・失敗・取消後に除去し、中断で残ったものは次回起動時に除去する。外部ファイルへの書込みはDBと一体のトランザクションにできないため、途中失敗時は不完全なファイルが残る可能性を案内する。今回作った外部文書以外を削除対象にしない。

### 8.3 CSV

UTF-8 BOM付き、改行CRLF、カンマ区切り、ヘッダーあり。文字列にカンマ・改行・二重引用符が含まれる場合は二重引用符で囲み、内部の二重引用符を2つにする。Booleanはtrue / falseとする。

### 8.4 外部加工側への契約

- 同じdataset_idの最新snapshot_revisionを全量の現在値として扱う。単純追加で再取込しない。
- 同一版の再出力はexported_atだけが違っても同じ業務内容。同じIDの新しいrevisionは修正である。
- 全クリア後は同じdataset_idの新しい版に空配列・METADATA行だけが入る。過去に書き出したファイルの内容は自動消去されない。
- 別のdataset_idは別のデータ集合として扱う。再インストール前後の同一業務データかどうかは推測しない。
- 対応しないschema_versionは黙って読み込まず、変換側で対応確認する。
- OPENの値は締め未確定。CLOSEDの値でも後から修正され得る。
- 本形式は帳簿作成の元データであり、既に確定した会計帳簿の削除・訂正を自動指示するものではない。重複・取消・訂正の反映は変換側で利用者に確認する。
- freee・弥生会計への変換、Uber側の明細照合、仕訳・税区分は別プロジェクトで設計する。

| --- | --- | --- |
| T-01 | 初回起動 | ホーム・レジ未開始。アプリ内ログインを要求しない |
| T-02 | 機内モード | 開始・計算・保存・編集・締め・ローカル保存先への出力が可能 |
| T-03 | 0円の初期釣銭 | 開始できる。同時に2つのレジを開始できない |
| T-04 | 商品1,500円・受取2,000円 | おつり500円、入金2,000円、出金500円、現金増加1,500円 |
| T-05 | 商品1,500円・受取1,500円 / 1,000円 | 前者はおつり0円で保存可。後者は500円不足で保存不可 |
| T-06 | 未入力、負数、小数、9,999,999超過、全角数字 | 不正値は保存不可。全角数字は正規化後に同じ規則で処理 |
| T-07 | 計算だけ行い画面を戻る | 保存ボタンを押さなければ明細は増えない |
| T-08 | 未開始 / 締め済みレジ | 未開始は計算のみ。締め済みには新規保存できない |
| T-09 | 保存の連打・保存後すぐ画面再生成 | 明細は1件。同じUUIDの再試行で二重記録しない |
| T-10 | 初期10,000円、T-04の取引、実残高11,400円、次回10,000円 | 予定11,500円、過不足-100円、手元増減1,400円、締め取出1,400円 |
| T-11 | 初期10,000円、回収1,500円、補充2,000円、途中取出1,000円 | 予定12,500円。補充を現金回収額に含めない |
| T-12 | 次回釣銭が実残高を超える / 過不足あり | 前者は締め不可。後者は差額を確認して締められる |
| T-13 | 明細0件で締め、日付をまたぐ稼働、同日2回の稼働 | 明細0件でも締め可。日付で自動締めせず、別レジで管理 |
| T-14 | 次回レジ開始 | 前回Nを候補表示し、開始操作で新しいFにコピー |
| T-15 | T-10の受取額だけ5,000円へ修正 | おつり3,500円。現金回収・予定残高・過不足は変わらない |
| T-16 | T-10の商品金額を1,000円へ修正 | 予定11,000円、過不足+400円。実残高・次回釣銭・後続レジFは維持 |
| T-17 | T-10の取引を取消 | 明細は取消表示。予定10,000円、過不足+1,400円。出力は取消状態と元金額を保持 |
| T-18 | 過去レジRをN未満へ編集 | Nも修正しなければ保存不可 |
| T-19 | 入力中の回転・文字拡大・横幅縮小 | 入力と対象レジを保持し、主要ボタン・結果を操作できる |
| T-20 | 保存途中終了・容量不足・古い版で編集 | 全件成功または全件未変更。成功を誤表示せず、競合を上書きしない |
| T-21 | 全クリアの取消 / 実行 | 取消時は無変更。実行時は稼働中を含む全業務履歴を消去し、未開始になる |
| T-22 | 全クリア後の出力 | dataset_id維持・全体版番号増加。JSON空配列、CSVメタ情報のみ。将来の課金導入後は購入情報を維持 |
| T-23 | 第8節のCSV / JSON照合 | 33列・関連ID・入力値・計算値が一致し、JSONを解析できる |
| T-24 | OPEN・取消済み・補充・取出しを出力 | 種別・未確定の空欄/null・取消状態を正しく表現 |
| T-25 | 出力中の編集 / 保存先取消 / 書込み失敗 | 一貫した出力時点。取消で元データ無変更。失敗を成功扱いしない |
| T-26 | 1万明細の履歴・出力 | 操作を止めずに表示・保存でき、集計漏れがない |
| T-27 | 再出力・同一明細編集後の出力 | 同じIDを維持。同じ全体版は同じ内容、変更後は新しい版 |
| T-28 | 通常起動と情報画面表示の通信監視 | 業務処理の通信・自動Billing接続・解析通信がない |
| T-29 | OSバックアップ・端末移行・アプリ更新 | 業務DBをバックアップ/移行しない。通常更新ではDBを保持する |
| T-30 | 問い合わせ | 正しい公開URLを外部で開く。顧客情報・金額・端末情報を自動付加しない |
| T-31 | 支援購入の成功・キャンセル・保留・再購入 | 適切な状態表示と消費。いずれでも無料機能に制限なし |
| T-32 | 購入成立後の中断・消費応答喪失・手動再確認 | トークン単位で再照合し、二重処理しない。未確認期限切れも確認 |
| T-33 | 個人用での課金無効・将来のPlay利用不可 | 個人用はボタン非表示・SDK未導入・購入通信なし。通常機能と履歴に影響なし |
| T-34 | 配布用成果物 | 個人用のManifest・同梱説明・OSS表示が実装と一致。署名付き公開版・ストア申告の確認は後日 |
| T-35 | 明細保存の完了通知前に中断し、対象レジを締めた後に保存を再試行 | 同じID・同じ内容なら成功済み。同じID・異なる入力金額なら競合。未保存IDなら締め済みとして拒否。いずれも明細件数・既存値・親レジと全体の版番号・締め日時を変更しない |
| T-36 | 新規Codespaceの再現性 | リポジトリから作成したCodespaceでJDK 17、Android SDK API 37、Gradle Wrapperが利用でき、`testDebugUnitTest lintDebug assembleDebug`が成功する |
| T-37 | CI Workflow | PRまたは通常のpushでcompile・Unit Test・Lintが実行され、失敗時は成功扱いにならない |
| T-38 | Distribution Workflow | `main`へのpushではCIのテスト・Lint成功後にAPKビルド・固定署名・Firebase App Distribution uploadが順に成功し、手動実行ではDistribution Workflow内の事前テスト・Lint成功後に同じ配布処理が成功する |
| T-39 | Firebase配布と更新 | 自分のテスターアカウントでAPKを取得でき、既存の個人用アプリをアンインストールせずに上書き更新できる。更新後も業務DBが残る |
| T-40 | Secrets保護 | Service Account JSON、keystore、パスワードがRepository、Actionsログ、Artifact、release noteへ出力されない |

金額計算は単体テスト、DBの一括保存・重複・編集競合はDBテスト、4画面の操作とファイル保存は画面・実機テストを中心に確認する。ネットワーク例外と購入中断は、通常の業務テストと区別して確認する。
