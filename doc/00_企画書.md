## 1. 目的

Uber Eatsの現金払いの配達で、持ち出した釣銭、顧客から受け取った現金、返したおつりをその場で記録し、稼働終了時に手元の現金を確認できるAndroidアプリを作成する。

現場で迷わず使える計算・記録を優先する。初期釣銭の登録から、おつり計算、レジ締め、帳簿作成に使う元データの出力までを、ログインなしの4画面で完結させる。

本アプリはUber Eatsの非公式な補助アプリであり、注文の取得、決済の実行、Uberへの送金、配達報酬の確定は行わない。

Mockup本人による個人運用を行い、問題がなければGoogle Play公開を検討する。開発者登録、公開用の署名鍵、課金商品の登録、ストア申請は公開準備時に行う。個人運用開始に必要なアプリを実装する。開発はGitHub Codespaces、ビルド・テスト・配布はGitHub Actions、個人用APKの配布はFirebase App Distributionを基本とする。

## 2. 解決する課題

| 場面 | 課題 | ウバレジでできること |
| --- | --- | --- |
| 稼働前 | いくら釣銭を持ち出したか分からなくなる | 初期釣銭を登録してレジを開始する |
| 現金受領時 | おつりの暗算と記録を同時に行いにくい | 商品金額と受取金額からおつりを表示し、受渡し後に記録する |
| 稼働中 | 追加した釣銭や取り出した現金が混ざる | 補充・取出しを顧客との取引とは別に記録する |
| 稼働後 | 手元現金と計算上の残高が合っているか確認しづらい | 予定残高・実残高・過不足を表示する |
| 次回稼働 | 次回に残す釣銭の金額が曖昧になる | 次回釣銭と取り出す金額を確定し、次回開始時の候補にする |
| 記帳時 | 手入力を繰り返し、元データを追いにくい | 独自仕様のCSV / JSONを出力する |

## 3. 想定利用者と利用条件

- 日本国内で日本円の現金払いを扱うUber Eatsの配達員。
- 1台の端末・1人の利用を想定する。複数人・複数端末の同期は行わない。
- Android 17（API 37）の安定版を対象に試作する。対象の根拠は基本設計書に記載する。
- 金額は1円単位。外貨、小数、金種別の枚数管理は扱わない。
- 配達先や顧客名を記録せず、金額と記録時刻を中心に扱う。

## 4. 利用の流れ

1. ホームから「レジ締め / 初期釣銭」を開く。
2. 初期釣銭を入力してレジを開始する。前回の次回釣銭があれば候補として表示する。
3. 「おつり計算」で商品金額とお客様支払金額を入力し、おつりを確認する。
4. 実際の現金受渡し後に「受渡しを記録」を押す。計算だけでは保存しない。
5. 必要に応じて、釣銭補充や現金取出しを記録する。
6. 稼働終了時に実際の手元現金を数え、予定残高との過不足を確認する。
7. 次回に残す釣銭を指定してレジを締める。
8. ホームからCSV / JSONを端末に保存する。必要な時に利用者自身が外部Webサイトで加工する。

「レジ」は開始から締めまでの1回の稼働単位とする。日付が変わっても自動で締めず、1日に複数回開始できる。

## 6. 現金管理と会計の境界

本アプリで扱う「現金回収額」は、顧客から受け取った金額からおつりを引いた額である。配達員の配達報酬や利益を意味しない。

- 初期釣銭・途中の補充は、手元現金への資金移動として扱う。
- レジ締めでは現金の増減・過不足・次回釣銭・取出額を計算する。
- 「収入」の要望は、試作では「現金回収額」「手元現金の増減」として表示する。配達報酬としての収入を確定するには、Uber側の明細など別の情報が必要になる。
- Uberへの支払・相殺・商品代金に関する処理、会計科目、税区分、仕訳生成はアプリ内で計算しない。
- freee・弥生会計への直接取込形式は作らない。別途開発・利用する外部Webサイトで、出力ファイルと必要な明細をもとに加工する。
- 本アプリ単体を正式帳簿、税額計算、電子帳簿保存要件に対応したシステムとして案内しない。

## 7. 収益化

- アプリ本体とすべての機能を無料で提供する。広告は表示しない。
- 将来の公開版では、アプリ情報画面に「開発を応援する」の購入ボタンを設ける。個人運用版は購入・購入確認ボタンを表示せず、課金SDKも組み込まない。
- 購入しても機能、履歴件数、出力範囲、表示内容の権利に差を設けない。
- Google Playの1回購入型商品を利用し、繰り返し支援できる消費型として設計する。定期購入は採用しない。
- 表示名は「開発支援（任意）」とし、税制上の寄付や控除対象であるかのような表示はしない。
- 商品IDは`developer_support`、表示名は「開発支援（任意）」、日本での設定希望価格は1回100円とする。Play Consoleへの登録は公開準備時に行い、その時点の価格設定・支払いポリシーに適合することを確認する。利用者への実際の価格表示はGoogle Playから取得する。
- 説明は「ウバレジの開発を任意で応援するための1回限りの購入です。すべての機能は購入せずに利用できます。機能の追加はありません。」とする。定期的な支払いは発生しない。
- 支援購入は配達業務の現金収支に混ぜず、CSV / JSONにも含めない。

## 8. ローカル保存・通信の方針

**2026-09-07に利用者確認済み：通常業務は完全オフラインとし、購入・問い合わせの操作時だけ通信を例外として認める。**

| 処理 | 方針 |
| --- | --- |
| 計算・記録・編集・レジ締め | 端末のアプリ専用内部領域で完結 |
| 広告・解析・エラー収集・同期 | 導入しない |
| OSによる自動バックアップ・端末移行 | 業務データを対象から除外する |
| CSV / JSON出力 | 利用者の明示操作でファイルを書き出す |
| Google Play購入 | 利用者の購入・購入確認操作を起点に接続。業務データは送信しない |
| 問い合わせ | 利用者の操作で外部ブラウザーを開く。投稿内容は利用者自身が入力する |

外部の保存先や変換サイトを利用者が選んだ場合、その後の通信・保存は選択先のサービスが行う。これはアプリによる自動送信とは区別して説明する。アプリ情報に「一切通信しない」とは記載しない。

## 9. 対象外

- Android 16以前、将来のAndroidメジャーバージョン、iOS向けの開発・動作保証。
- Uberアカウントとの連携、注文取込、商品代金の自動照合、送金代行。
- ログイン、独自サーバー、クラウド保存、複数端末同期、顧客管理。
- 会計ソフト専用CSV、会計API連携、外部変換Webサイトそのものの開発。
- ファイルの再取込・復元、金種管理、顧客からのチップ管理、掛け・分割払い。

将来の展開は別途検討する。試作にそのための抽象化や画面を先行追加しない。

## 11. 試作完了の判断

1. 機内モードでも初期釣銭の登録から計算・記録・編集・締め・ローカル出力まで完了できる。
2. おつり、残高、過不足、次回釣銭が詳細設計書の計算例と一致する。
3. 再起動後も保存済み履歴が残り、保存の連打や途中終了で二重記録しない。
4. 履歴編集が集計と出力に反映され、過去の修正が別のレジを勝手に書き換えない。
5. CSV / JSONから現金の流れと各レジの締め結果を追える。
6. 購入しない利用者もすべての業務機能を使える。

Google Playへの公開完了は試作完了とは別の段階とし、課金試験・必要な審査準備を追加して判断する。

個人運用版の完了判断では、課金の成功・保留等の試験を対象外とし、課金なしで全業務機能を利用できることを確認する。運用期間の目安と記録方法は[40_公開・運用手順](40_公開・運用手順.md)に従う。
