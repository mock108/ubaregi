## 1. 基本の進め方

**1段階ずつ「AIが実装・検証 → 本人が画面を確認 → 修正して保存」を繰り返す。** 本人がコードを一行ずつ読むことを前提にせず、金額が合うこと、入力しやすいこと、記録が残ることを確認する。

AIへの依頼は、このプロジェクトのファイルを読み書きできる環境で行う。設計書を毎回貼り直す必要はなく、本書のファイル名と段階番号を伝える。実際の配達記録や署名鍵を会話に貼らず、確認には架空の金額を使う。

| AIに任せること | 本人が行うこと |
| --- | --- |
| 設計書の確認、構成・依存の選定、コード作成 | 作る機能や使い勝手への希望を伝える |
| ビルド、自動テスト、エラー調査と修正 | 初回導入時の必要な操作、実機のUSB接続・端末側の許可 |
| 画面確認手順、APKの場所の案内 | 端末で入力し、おつり・履歴・操作性を確認する |
| 差分レビュー、コミット、依頼されたPush・Pull Request作成 | 確認結果を伝え、問題がなければ取り込みを依頼する |

Google Play登録、公開用署名鍵、購入機能、外部変換サイトはこの手順の対象外とする。個人用は全業務機能無料・課金無効で作る。将来の公開準備は[40_公開・運用手順](40_公開・運用手順.md)で扱う。

## 2. 各段階でAIが守る共通条件

以下は第3節のすべての依頼文に適用する。短い依頼文を使う場合も、最初に本書を読むよう伝える。

1. [企画書](00_企画書.md)、[基本設計書](10_基本設計書.md)、[詳細設計書](20_詳細設計書.md)、[開発環境構築手順](30_開発環境構築手順.md)を確認し、現在のファイルと進捗を調べてから着手する。
2. 単一アプリモジュール、Kotlin・Compose・Room、4画面を維持する。通常業務はオフラインとし、ログイン・広告・解析・課金SDKを追加しない。初期釣銭や回収額を配達報酬として扱わない。
3. 細かい実装方法はAIが設計に沿って決める。追加機能や別の構成に広げず、未完了の段階を飛ばさない。
4. 既存の変更を確認して保護する。段階ごとに作業ブランチを1つ使い、同じ作業コピーで複数のAIに同時編集させない。前段階の取り込み後、その状態から次の段階を始める。
5. ビルドと変更に関係するテストを実行し、失敗したら原因を調べて修正する。実行できない確認は、理由と未確認部分を明記する。未実施のテストを合格と記載しない。
6. 保存済みデータ、SDK設定、署名鍵を消してエラーを回避しない。DB更新時は既存データを維持し、個人用アプリのIDとデバッグ鍵を保つ。
7. 実装と設計の差が必要になった場合は理由を示し、合意済みの要件を勝手に変更しない。採用した依存の版や実施結果は関係する文書に反映する。
8. 完了時は「できたこと」「確認結果」「本人が試す操作」「残件」を短く報告する。ビルドできた場合はAPKの実際の場所も案内する。

各段階の最初の依頼では実装とローカル検証までを進める。本人の確認後に、第4節の依頼文で公開ブランチへ保存し、レビューして取り込む。Pushやレビューのために実際の配達データを公開しない。

## 3. 開発の5段階

### 段階1：開発環境と起動するアプリ

最初は、端末で4画面を行き来できる土台を作る。AIが環境を調べ、[開発環境構築手順](30_開発環境構築手順.md)の版を基準に設定する。導入や端末接続に本人操作が必要な場合は、その操作だけ案内してもらう。

AIへの依頼文：

```text
doc/60_AI活用開発手順.mdを読み、共通条件に従って段階1を実装してください。
既存の開発環境を確認し、必要な環境を整えてAndroidプロジェクトと4画面の遷移を作成してください。
依存バージョンを固定し、個人用debug APKのビルドまで確認してください。
アプリ情報にはMockup、実際のバージョン、個人用の説明、同梱プライバシーポリシーとOSS表示を用意してください。
まだ動かない業務操作は無効化し、保存できたような表示を出さないでください。
本人の操作が必要な部分は、具体的な操作だけ案内してください。
```

本人の確認：アプリが起動する、4画面を移動して戻れる、文字を読める、開発者名がMockupになっている。初回の空データで確認する。

完了条件：debug APKがビルドでき、エミュレーターまたは実機で起動を確認できる。利用できなかった端末環境は未確認として残す。

### 段階2：開始・おつり計算・レジ締め

毎日の基本操作を一通り使えるようにする。DBと計算関数だけを作って終わらせず、4画面から実際に操作できるところまでつなぐ。

AIへの依頼文：

```text
doc/60_AI活用開発手順.mdの共通条件に従って段階2を実装してください。
Roomによる保存、初期釣銭の登録、おつり計算、受渡し記録、補充・取出し、レジ締め、次回釣銭候補を画面から使えるようにしてください。
詳細設計書の計算式と保存契約に従い、再起動後の保持と保存の重複防止も実装してください。
計算・保存のテストを実施し、特にT-35の締め後の保存再試行も確認してください。
本人が端末で試す一連の操作と期待する金額を案内してください。
```

本人の確認：初期釣銭10,000円、商品1,500円、受取2,000円で、おつり500円・予定残高11,500円になる。実残高11,400円・次回釣銭10,000円で締め、過不足-100円・取出額1,400円になる。アプリを開き直しても記録が残る。

完了条件：未開始から締めまで実行でき、未入力・受取不足・保存の連打で誤記録しない。ここでは架空データを使い、実運用はまだ始めない。

### 段階3：履歴の確認・編集・取消

AIへの依頼文：

```text
doc/60_AI活用開発手順.mdの共通条件に従って段階3を実装してください。
レジ履歴、受渡し履歴、補充・取出し履歴の表示と編集・取消、全履歴クリアを完成させてください。
締め済みへの新規明細追加は禁止し、過去の編集で後続レジの初期釣銭を自動変更しないでください。
取消済み明細の扱い、保存前の確認、古い画面からの更新、全クリア後の下書き破棄を検証してください。
この段階の本人確認は架空データだけで行える手順にしてください。
```

本人の確認（すべて架空データ）：

1. 端末に残っている試験記録だけを対象に「全履歴をクリア」を開き、キャンセルして記録が残ることを確認する。確認ダイアログの件数と稼働中レジの表示も見る。
2. 初期釣銭10,000円でレジを開始し、商品1,500円・受取2,000円を保存する。おつり500円、予定残高11,500円、受渡し履歴1件を確認する。
3. 「釣銭を補充」で1,000円を保存し、予定残高12,500円になることを確認する。補充履歴を700円へ編集し、保存前の確認で表示される金額を確認して保存する。予定残高は12,200円になる。続けて取消し、元の1,000円が「取消済み」として残り、予定残高が11,500円へ戻ることを確認する。
4. 実残高11,400円・次回釣銭10,000円で締める。予定残高11,500円、過不足-100円、締め時の取出額1,400円を確認する。締め済みのレジ履歴から「このレジの取引を見る」を開き、新規受渡し保存が無効になっていることを確認する。
5. 締め済みレジの受渡し履歴で商品金額を1,000円へ編集し、保存前の確認を経て保存する。予定残高11,000円、過不足+400円になる一方、実残高11,400円・次回釣銭10,000円は変わらないことを確認する。編集した明細を取消すと、予定残高10,000円、過不足+1,400円になり、取消済みの元金額が残ることを確認する。
6. 「レジ締め / 初期釣銭」へ戻って次のレジを初期釣銭10,000円で開始する。前のレジを編集しても、次のレジの初期釣銭が10,000円のまま変わらないことを確認する。
7. おつり計算で商品123円・受取500円を入力したまま保存せず、ホームへ戻る。「全履歴をクリア」で表示件数を確認して実行し、未開始画面になり、履歴・稼働中レジ・入力中の下書きが消えることを確認する。アプリを開き直しても空のままであることを確認する。

古い画面からの更新は、Roomテストで同じレジ・明細を別のrevisionから編集し、競合として拒否されて値を上書きしないことを確認する。端末では上記の保存前確認と画面更新後の表示を確認し、実データは使わない。

完了条件：選択したレジだけを編集でき、集計に反映される。締め済みへの新規追加がなく、取消済み明細が元金額付きで残り、後続レジの初期釣銭が変わらない。取消・全クリアの確認でキャンセルすると元データが維持され、全クリア実行後は下書きも破棄される。端末未接続で未確認の項目は完了扱いにしない。

### 段階4：CSV / JSON出力

AIへの依頼文：

```text
doc/60_AI活用開発手順.mdの共通条件に従って段階4を実装してください。
詳細設計書第8節の独自CSV / JSON出力を完成させてください。
CSVは固定33列、JSONと同じ業務内容とし、OSの保存先選択からファイルを書き出せるようにしてください。
空履歴、稼働中、締め済み、取消、補充・取出し、再出力、出力中の編集を確認してください。
全クリア時の「ホームで先に出力」も確認し、形式の解析・値の一致・保存取消・保存失敗を検証してください。
会計ソフト専用形式や外部変換サイト、再取込機能は追加しないでください。
```

本人の確認：端末内にCSVとJSONを保存できる。ファイルを開くと架空のレジと明細を確認できる。保存先選択をキャンセルしても履歴が消えない。

完了条件：詳細設計書の形式と一致し、成功時だけ保存完了と表示する。書き出したファイルをアプリへ戻す機能はないことを説明に明記する。

### 段階5：個人運用前の仕上げ

AIへの依頼文：

```text
doc/60_AI活用開発手順.mdの共通条件に従って段階5を進めてください。
現在の実装を設計書と照合し、不具合と未実装を確認して修正してください。
詳細設計書のT-01〜T-30・T-33・T-34の個人用部分とT-35を対象に確認してください。
課金導入後だけの項目は対象外とし、実施結果をdoc/40_公開・運用手順.mdに記録してください。
機内モード、再起動、更新時のデータ保持、バックアップ除外、文字拡大、1万明細を確認してください。
本人の実機でしか確認できない点は未確認として具体的な手順を示し、個人運用へ進めるか判定してください。
```

本人の確認：機内モードでも開始から締め・端末内出力まで操作できる。屋外で金額を読みやすい、入力欄や保存ボタンを押しやすい、保存後に次の金額を入力しやすいことを確認する。画面を見ながらの操作は安全に停止した状態で行う。

完了条件：個人用の受入確認が完了し、計算間違い・記録消失・二重保存・出力不整合が残っていない。未確認項目があれば完了扱いにせず、必要な確認を終えてから[個人運用](40_公開・運用手順.md)へ移る。

## 4. 各段階の確認・保存・取り込み

AIが実装を終えたら、案内された操作を端末で試す。問題があれば第5節の形で伝える。問題がなければ、次の依頼を使う。

```text
この段階の画面確認は問題ありませんでした。
差分を確認して、この段階の変更を作業ブランチへコミット・Pushし、Pull Requestを作成してください。
実データ・鍵・端末固有の設定を含めず、できたことと実施した確認を説明に記載してください。
```

続いて、同じ会話でレビューを依頼する。長くなって確認しづらい場合は、同じプロジェクトの別の会話へPull RequestのURLを渡して依頼してもよい。同じファイルの実装とレビュー修正を同時に進めない。

```text
このPull Requestを設計書と照合してレビューしてください。
計算、保存の重複、履歴編集、データ消去、通信、設計外の機能追加を重点確認してください。
問題があれば修正し、修正に関係する確認を再実施してください。
必要な確認が完了し、未解決の問題がなければmainへ取り込んでください。
```

取り込み後に次の段階へ進む。リポジトリの権限・保護設定によりAIが実行できない操作は、原因と本人が押す操作を案内してもらう。mainへの取り込みはGoogle Playへの公開ではない。

各段階で依頼する完了報告は次の4点に揃える。長い会話の引継ぎにも使う。

- 完了した段階と、変更した機能。
- 実際に行った確認と、その結果。未実施は理由を添える。
- 作業ブランチ・コミット・Pull Requestと、ビルドできたAPKの場所。
- 本人の確認結果、残件、次に着手する段階。

## 5. エラーや使いにくさの伝え方

コードを推測して直す必要はない。「何をしたら、どうなったか」を伝える。エラーは要約だけでなく、機密情報を除いた実際のメッセージを渡す。

```text
段階：2
端末・アプリ版：実際の端末名とアプリ情報の版
操作：商品1,500円、受取2,000円を入力して「受渡しを記録」を押した
期待：おつり500円が表示され、履歴が1件増える
実際：表示された内容やエラーを記載
再現：毎回 / ときどき / 一度だけ

設計書と実装を確認し、原因を調べて修正してください。
保存済みデータを消さずに対応し、修正を確認するテストと本人の確認手順を示してください。
```

使い勝手の修正は「おつりの文字を大きく」「保存後に商品金額へ戻してほしい」のように、困る場面と希望を伝える。AIは既存の仕様と照合し、必要な範囲だけ修正する。

ビルドエラーは、まずAIがその環境で再現して原因を調べる。本人が別サイトの手順で依存バージョンを次々と変えると状態を追いにくくなるため、変更は一度に一つの原因へ絞り、動いた組合せを保存する。

## 6. 個人運用へ移った後

[40_公開・運用手順](40_公開・運用手順.md)に従い、まず本人が使う。目安の2週間・10回のレジ締めだけで自動的に公開せず、使い勝手と記録の正しさを確認する。

日々の出力は本人が保管し、AIには架空の値で再現した不具合を伝える。更新前には記録を書き出し、同じ個人用アプリID・デバッグ鍵で更新する。公開版への自動移行・JSONからの復元は初期版にはない。

Google Playへの公開を決めた時点で、登録・公開用署名・開発支援購入・ストア情報の準備へ進む。本人確認や秘密情報の入力はその時点で行い、この開発手順に先行して追加しない。
